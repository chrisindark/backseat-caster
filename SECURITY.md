# 🔒 BackseatCaster — Security

BackseatCaster is a **local-first, single-operator tool**. The assumed threat model is your own machine (or a self-hosted Docker host), not a multi-tenant internet service. Keep the app bound to localhost unless you understand the implications below.

---

## 1. Secrets & Credentials

| Secret | Location | Notes |
|---|---|---|
| Google OAuth client config | `./data/client_secrets.json` (or inline `YOUTUBE_CLIENT_ID` / `YOUTUBE_CLIENT_SECRET`) | User-provided; gitignored |
| OAuth token | `./data/youtube_token.json` | Written after first consent; revoked via `POST /api/v1/youtube/auth/revoke` |
| SQLite DB | `./data/backseatcaster.db` | Catalog + job state only; no secrets stored |

- All of `./data` is gitignored — never commit credentials, tokens, or client secrets.
- Secrets are read once per request path via `Settings` properties; there is no runtime secret store.
- Token storage/refresh/removal is centralized in `YouTubeUploaderService`. Prefer revoking over hand-deleting the token file.

---

## 2. OAuth Scope Discipline

The YouTube uploader authenticates with the minimum OAuth scopes required for publishing (via `google-auth-oauthlib` flow). The consent URL is generated by the backend (`GET /api/v1/youtube/auth/url`) with `YOUTUBE_REDIRECT_URI` fixed to the backend's own callback endpoint. Do not widen scopes without updating `docs/youtube-authentication.md`.

---

## 3. Network Exposure

- Default bind is `127.0.0.1:3001` (configurable via `HOST`/`PORT`).
- **CORS** is whitelist-based (`CORS_ORIGINS`, default `localhost:3000`). Setting `CORS_ORIGINS` to a non-list value falls back to a wildcard — avoid in any non-local deployment.
- **No authentication** exists on the API itself. If you expose the backend beyond localhost, put it behind an authenticating reverse proxy; otherwise any LAN peer can trigger downloads, renders, reads of local media, and (when OAuth is linked) YouTube uploads/deletions.
- `GET /videos/{id}/stream` and `/renders/{clip_id}/stream/{video_type}` serve files from `./data/downloads` and `./data/renders` respectively — treat these paths as trusted-input-only.

---

## 4. Filesystem Attack Surface

Media tooling shreds arbitrary files, so:

- **Upload validation:** `POST /api/v1/videos/upload` accepts media extensions (`.mp4`, `.mkv`, `.mov`, `.webm`, ...) — unsupported types are rejected with `400`.
- **Downloads:** yt-dlp results land only under `./data/downloads`.
- **Renders:** FFmpeg never receives user-controlled arguments beyond validated render parameters (`app/rendering/validator.py`); invalid combos are rejected before command construction.
- All path handling uses `pathlib.Path` with configured, resolved roots — no raw string concatenation of user input into paths.

---

## 5. Safe Testing Practices

- Tests never hit the network: they load synthetic FFmpeg assets generated via `lavfi` (`testsrc`/`testsrc2` + `sine`) and in-memory SQLite.
- `tests/test_youtube_upload.py` uses stubs/mocks for Google APIs — no test writes a real token file or performs a real upload.

---

## 6. Dependency & Supply Chain

- Lockfile (`uv.lock`) pins the Python dependency tree; commit it and keep it in sync via `uv sync`.
- Update deliberately: `yt-dlp` and FFmpeg versions affect extraction/filter behavior, so pin and test upgrades rather than floating.
- `pre-commit` + `ruff` guard formatting/lint drift only — dependency auditing for your environment is manual (e.g., `uv audit` where available).

---

## 7. Reporting Issues

Security problems (credential handling, SSRF in yt-dlp flows, path traversal, etc.) should not be filed publicly with exploit details. Open a GitHub issue titled `security: <summary>` with reproduction steps removed, or contact the maintainers directly — see [CONTRIBUTING.md](CONTRIBUTING.md).
